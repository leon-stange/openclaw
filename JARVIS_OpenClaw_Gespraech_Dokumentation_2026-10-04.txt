ZIEL
----
Ziel des Projekts war es, den bisher auf einer Windows-VM laufenden persönlichen
JARVIS-Assistenten auf einen frisch installierten Ubuntu-24.04-Server zu übertragen
und dort dauerhaft zu betreiben.

Der gewünschte Funktionsumfang:

- OpenClaw als zentraler Agent
- OpenAI / ChatGPT als Modellzugang
- Standardmodell: openai/gpt-5.6-sol
- WhatsApp als Kommunikationskanal
- nur die private Owner-Nummer darf Jarvis steuern
- keine WhatsApp-Gruppen
- ElevenLabs für TTS
- MeowCaller für WhatsApp-Sprachanrufe
- eingebauter WhatsApp-Anruf an den aktuellen Absender
- eigenes Plugin für Anrufe an vorher freigegebene Kontakte
- Beispielkontakt: Annka
- OpenClaw als systemd-User-Service
- Autostart auch ohne SSH-Login
- kein öffentlich freigegebener Gateway-Port

6. WHATSAPP-PLUGIN
============================================================

WhatsApp wurde über das offizielle OpenClaw-Plugin installiert:

openclaw plugins install @openclaw/whatsapp

Die Jarvis-WhatsApp-Nummer ist eine separate WhatsApp-Business-Nummer.

Die private Owner-Nummer wurde als einziger erlaubter Absender eingetragen.

Wichtige Konfiguration:

{
  "channels": {
    "whatsapp": {
      "enabled": true,
      "dmPolicy": "allowlist",
      "allowFrom": [
        "+49..."
      ],
      "groupPolicy": "disabled",
      "mediaMaxMb": 50,
      "actions": {
        "calls": true
      }
    }
  },
  "commands": {
    "ownerAllowFrom": [
      "whatsapp:+49..."
    ]
  }
}

Wichtiger Fehler während der Einrichtung:
-----------------------------------------

Beim ersten Versuch wurde folgender Befehl falsch verwendet:

read -rp "+49..." OWNER_NUMBER

Der Text "+49..." war dabei nur der Prompt-Text. Die Variable blieb leer.

Dadurch wurde fälschlich gespeichert:

channels.whatsapp.allowFrom = []

und:

commands.ownerAllowFrom = ["whatsapp:"]

Erkennbar an:

openclaw config get commands.ownerAllowFrom --json

Ausgabe:

[
  "whatsapp:"
]

Korrekte Verwendung:

read -rp "Deine private WhatsApp-Nummer im Format +49...: " OWNER_NUMBER

Danach die Nummer wirklich eingeben.

Prüfungen:

openclaw config get channels.whatsapp.allowFrom --json
openclaw config get commands.ownerAllowFrom --json

============================================================
11. TTS-PROBLEM UND LÖSUNG
============================================================

Zwischenzeitlich meldete Jarvis:

"Für Sprachausgabe ist aktuell kein TTS-Anbieter konfiguriert."

Obwohl:

openclaw config get tts --json

bereits zeigte:

provider: elevenlabs

Die Ursache war, dass der systemd-Service die Datei:

/home/leon/.openclaw/gateway.systemd.env

noch nicht einlas.

Lösung:

mkdir -p /home/leon/.config/systemd/user/openclaw-gateway.service.d

cat > /home/leon/.config/systemd/user/openclaw-gateway.service.d/environment.conf <<'EOF'
[Service]
EnvironmentFile=/home/leon/.openclaw/gateway.systemd.env
EOF

Dann:

systemctl --user daemon-reload
systemctl --user restart openclaw-gateway.service

Prüfen:

systemctl --user show openclaw-gateway.service -p EnvironmentFiles

Zusätzlich konnte geprüft werden, ob der laufende Gateway-Prozess den Key wirklich hat:

PID=$(systemctl --user show openclaw-gateway.service -p MainPID --value)
sudo tr '\0' '\n' < /proc/$PID/environ | grep -q '^ELEVENLABS_API_KEY=' && echo "OK: Gateway hat ElevenLabs-Key" || echo "FEHLER: Gateway hat keinen ElevenLabs-Key"

Später zeigte WhatsApp bei:

/tts status

korrekt:

State: disabled
Provider: elevenlabs (configured)
Auto-summary: on

Damit war die ElevenLabs-Konfiguration erfolgreich.

Das Plugin:

- erlaubt nur vorher konfigurierte Kontakte
- gibt dem Modell keine freie Telefonnummernwahl
- nutzt ElevenLabs für TTS
- nutzt MeowCaller für den eigentlichen WhatsApp-Anruf

- hat Rate-Limiting
- löscht temporäre Audiodateien wieder
- verwendet OpenClaw-Owner-Autorisierung


============================================================
13. WICHTIGER PLUGIN-FIX: senderIsOwner
============================================================

Die erste Version des Plugins prüfte sinngemäß:

toolContext.requesterSenderId

gegen eine E.164-Telefonnummer.

Das war unter WhatsApp problematisch, weil OpenClaw teilweise eine WhatsApp-LID/JID
statt direkt der E.164-Nummer liefert.

Dadurch war das Tool in WhatsApp nicht verfügbar, obwohl das Plugin geladen war.

Die korrigierte Lösung:

if (toolContext.messageChannel !== "whatsapp") return null;
if (toolContext.senderIsOwner !== true) return null;

Damit verwendet das Plugin die von OpenClaw selbst verifizierte Owner-Identität.

Wichtig:
--------
commands.ownerAllowFrom muss korrekt gesetzt sein.

Beispiel:

[
  "whatsapp:+49..."
]

19. SYSTEMD-PERMISSION-PROBLEM
============================================================

Fehler:

OpenClaw erkannte, dass:

~/.config/systemd/user

oder ein übergeordneter Ordner gruppen- oder welt-schreibbar war.

Prüfung:

stat -c '%a %U:%G %n' /home/leon /home/leon/.config /home/leon/.config/systemd /home/leon/.config/systemd/user

Ergebnis u. a.:

775 leon:leon /home/leon/.config

Außerdem existierten:

/home/leon/.config/systemd
/home/leon/.config/systemd/user

noch nicht.

Lösung:

chmod 700 /home/leon/.config
mkdir -p /home/leon/.config/systemd/user
chmod 700 /home/leon/.config/systemd
chmod 700 /home/leon/.config/systemd/user

sudo chown leon:leon /home/leon/.config
sudo chown leon:leon /home/leon/.config/systemd
sudo chown leon:leon /home/leon/.config/systemd/user

1. Bei "read -rp" muss die Nummer nach dem Prompt wirklich eingegeben werden.
2. commands.ownerAllowFrom ist unabhängig von channels.whatsapp.allowFrom.
3. Für das eigene Plugin ist senderIsOwner zuverlässiger als rohe WhatsApp-Sender-IDs.
4. MeowCaller benötigt eine eigene WhatsApp-Linked-Device-Session.
5. Ein Shell-PATH ist nicht automatisch identisch mit dem PATH eines systemd-Service.
6. OpenClaw verweigert systemd-Installationen bei unsicheren Verzeichnisrechten.
7. ElevenLabs kann in OpenClaw korrekt konfiguriert sein, während der Gateway den API-Key noch nicht kennt.
8. gateway.systemd.env muss vom systemd-Service tatsächlich geladen werden.
9. tts.auto=off verhindert nicht die gezielte TTS-Nutzung in whatsapp_call.
10. Ein echter systemd-Service ist für einen dauerhaften Ubuntu-Server deutlich besser als ein Foreground-Prozess.
